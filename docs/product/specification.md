# AIファクトリー MVP仕様書

ステータス: 検討中 / 作成日: 2026年10月31日

## 1. 目的と対象

AIを活用したプロダクト開発基盤を、まず個人向け（ToC）のWebアプリとして実験する。第一段階のMVPではGitHub情報をチャットで読み取り、コンテキスト肥大を抑える仕組みを検証する。

第二段階ではPRの自動レビューと、ユーザーのリクエストに基づく実装・PR作成に拡張し、将来的にはGitHub上のより広い開発作業を扱う。

## 2. 合意済みの方針

- インフラはGCPを利用する。

- ユーザーはGitHubでログインし、GitHub MCP経由の操作を行う。

- AIは初期版でOpenAI APIを利用し、ユーザーが自身のAPIキーをセッションごとに入力する。

- AI認証情報は受領から最大1時間以内、またはセッション終了時に削除する。

- ジョブ基盤は使わず、接続中のチャットセッションでAIエージェントを動かす。WebSocketで指示・停止を送り、進捗を受け取る。

- 将来はVertex AIを利用し、アプリ側でユーザー別のクレジットを管理する構想がある。MVPでは決済・クレジット機能は実装しない。

## 3. 第二段階の想定利用フロー

1. ユーザーがGitHubでログインする。

2. GitHub Appにレビュー対象リポジトリへのアクセスを許可する。

3. OpenAIのAPIキーを入力し、利用するモデルを選択する。

4. PR URLを入力し、チャットでレビュー観点を指定する。

5. AIエージェントがPRの差分や必要な関連コードを取得し、レビューを実行する。

6. ユーザーは進捗を確認し、追加指示・質問・停止を行える。

7. AIは指摘箇所、問題の説明、影響、必要に応じた修正案を提示する。

8. ユーザーが投稿内容を選択・確認・編集したうえで、GitHubへ投稿する。

## 4. 共通基盤と第二段階の機能要件

### 4.1 GitHub連携

- GitHub.comのPR URLを受け付ける。公開・非公開リポジトリを対象とする。

- GitHub Appに対し、ユーザーが対象リポジトリを選んでアクセスを許可する。

- GitHub MCP経由で、PR情報、差分、必要な関連ファイルや既存コメントを取得する。

- ユーザーがアクセス可能なリポジトリに操作を限定する。GitHub Appのユーザーアクセストークンの利用を第一候補とし、認証・権限の詳細は実装前に検証する。

- GitHubへのコメント投稿は、ユーザーが確認して明示的に実行した場合に限る。投稿に必要な書き込み権限は明示し、許可を得る。

- レビュー対象のPRとコミットを記録し、PR更新により結果が古くなった場合は通知する。投稿時の最新コミット確認方法は実装時に決める。

### 4.2 レビューとチャット

- レビュー観点を自由文で指定できる。

- 指摘には対象ファイル・行、説明、影響、重要度を可能な限り付ける。

- 指摘に対する質問や追加のレビュー観点をチャットで受け付ける。

- レビュー対象としたコミット、結果、会話履歴を後から確認できる。

- 初期版ではリポジトリ内のコードやテストを実行しない。PRレビューではコード変更を行わない。コード変更とPR作成は第13節の実装・PR作成機能に限り、マージと本番デプロイは対象外。

### 4.3 チャットセッションと介入

- ブラウザはWebSocketで依頼・追加指示・停止を送信し、進捗・状態・結果をリアルタイムに受信する。接続を受けたインスタンスがそのセッションの実行を担当し、入力受付とエージェント処理を非同期に進める。

- 追加指示を受け付け、処理の安全な区切りで反映する。

- 停止は実行中の処理にキャンセルを要求し、新しい処理の開始を止める。即時停止を保証せず、停止中と停止済みを表示する。完了済みの外部操作は自動的には取り消されない。

- 状態は、受付済み、実行中、ユーザー待ち、AI認証待ち、完了、停止中、停止済み、失敗を基本とする。

- 会話・進捗・結果を保存し、WebSocket切断時はAIを使う処理を停止または認証待ちにする。ブラウザは自動再接続し、保存済み状態を復元する。キーがメモリに残っていれば安全に再送し、なければ再入力する。インスタンス終了時は保存した最後の区切りから再開できるようにし、同一セッションの二重実行を防ぐ。

- 失敗・再試行時は操作の重複を防ぎ、特にGitHubへの重複投稿を防ぐ。

## 5. AI認証と費用

- MVPではユーザーが自身のOpenAI APIキーを入力し、その利用枠でAIを呼び出す。ChatGPTの契約とAPIの利用経路は別であること、API利用に料金が生じ得ることを画面に明示する。

- APIキーはブラウザのメモリに保持し、必要な呼び出し時にTLSでサーバーへ渡す。ブラウザの永続ストレージ、会話履歴、ログ、URLには保存しない。

- サーバーは受領したキーを当該呼び出しに必要な間だけメモリで扱い、永続保存しない。処理終了時に参照を破棄する。

- 受領から最大1時間、またはセッション終了時の早い方で利用を停止し、保持するコピーを破棄する。期限到達後に続行する場合は再入力を求める。アプリが保持するコピーの削除と、OpenAI側でキーを失効させることは別である。

- 切断時はAIを使う処理を停止または認証待ちとする。ブラウザを閉じてもレビューを続行することはMVPの保証対象外。

- 将来のOpenAI OAuth対応は、Webアプリでの利用資格・権限・利用条件を確認してから検討する。サインインだけではAI利用の認可にならない。

## 6. 安全性とプライバシー

- ユーザーごとにセッション、会話、レビュー結果を分離する。WebSocket接続時に認証・認可とOriginを検証し、セッションへのアクセス時とGitHub操作時にユーザーの権限を確認する。

- GitHubログインは安全なOAuthフローを使い、セッション保護、CSRF対策、XSS対策を行う。認証情報をログ・監視データに出さない。

- PR本文、コード、コメントなどは信頼できない入力として扱い、その中の命令によって権限を拡張したり、情報を外部送信したりしない。

- 非公開コードを含むレビュー対象データがOpenAIへ送信されることを、実行前にユーザーへ明示する。

- GitHubおよびAIの認証情報は別に管理する。GitHubログインの有効期間・トークン更新・失効時の扱いは別途定義する。

- 会話、レビュー結果、取得したコードの保存期間・削除方法、第三者提供に関する説明を定める。

## 7. GCP構成案

以下は実装に向けた第一候補であり、実現性と安全性の検証後に確定する。

- Webアプリ: チャット、PR入力、進捗・レビュー表示、ユーザー操作、AIキーの一時保持。

- Cloud Runサービス: GitHub認証、WebSocket接続管理、セッション管理、オーケストレーター、AIエージェント、認証情報の一時受け渡し、OpenAI APIとGitHub MCPへの接続を担当する。通信とエージェントは同じサービス内の別モジュールとする。

- オーケストレーターはPR取得、差分確認、関連ファイル取得、AIレビューを適切なステップに分割し、各区切りで状態を保存して追加指示・停止要求を確認する。進行中の応答への即時反映は保証しない。通信方式と処理制御を分離する。

- Firestore: セッション状態、会話、レビュー結果、対象PR・コミット、利用量の保存。

- GitHub AppとGitHub MCP: ユーザーの許可に基づくPR取得とコメント投稿。

- Cloud Logging / Monitoring: 進捗・障害・セキュリティの監視。秘密情報や不要なコードを記録しない。

WebSocket接続にはCloud Runのリクエスト期限があり、再接続先のインスタンスは保証されない。接続が確立している間は同一インスタンス内で通信とエージェントを連携させる。永続状態からの再接続と復元、切断後の明示的な停止・認証待ち、キーの安全な再送、複数タブや古い実行主体による二重実行防止を詳細設計・検証する。接続時間と同時接続数による費用を実測する。

- クレジットの購入・付与・課金・残高不足・失敗時の返還は将来決定する。

- レビュー実行とユーザーに紐づけて、モデルや取得できたトークン数などの利用量を記録する。モデル別の料金換算やクレジットの計算方法は将来定義する。

- 実装・PR作成（第13節）に加え、Issue対応やCI失敗の修正など、より広い開発タスクへ拡張する。

- 隔離した実行環境でのビルド・テスト実行と、その結果に基づく修正。

## 10. 第二段階（PRレビュー）の確認条件

- GitHubログイン後、許可したリポジトリのPRを指定してレビューを開始できる。

- OpenAI APIキーをセッションごとに入力でき、期限切れ・接続切断時には認証待ちとなる。

- 指定したPRの対象コミット、進捗、レビュー指摘を確認できる。

- 実行中の追加指示と停止を行える。

- ユーザーが選択・確認した内容だけをGitHubに投稿できる。

- 他ユーザーのセッションや結果を参照できず、認証情報が永続ストレージやログに残らないことを検証する。

## 11. PRレビューフロー設計（仮案）

### 前提

- 通常サイズのテキスト中心のPRを扱う。大きな画像、動画、バイナリ、生成ファイルは対象外とする。

- ユーザーがPR URLと任意のレビュー観点を入力し、途中で追加指示・停止を行える。

- コードやテストの実行は行わない。GitHubへの投稿はユーザーが確認した後に行う。

- 以下の数値は検証前の仮置きで、実際のPRとメモリ使用量を測定して調整する。

### 処理手順

1. PRタイトル、説明、ベースとヘッドのコミット、変更ファイル一覧・変更量、対象となるテキスト差分をGitHub MCPから取得する。既存コメントは必要に応じて取得する。開始時の対象コミットを固定し、対象外としたファイルを記録する。

2. 関連する機能やディレクトリごとにファイルをグループ化し、レビュー計画と実行順を作成する。1ステップあたり原則最大10ファイルとし、変更量が大きい場合はさらに分割する。

3. PRの目的、ユーザーの指示、対象グループの差分、必要最小限の周辺コード、関連する既存の指摘・要点をAIに渡す。実際に起き得るバグ、認証・認可などの問題、既存処理との不整合、重要なテスト不足を確認する。

4. 判断に必要な場合、対象コミットの関連コードをGitHub MCPから追加取得する。仮の上限は1ステップ最大5ファイル、1ファイル最大100 KiB。AIに渡す入力にも別途上限を設定する。取得・確認できなかった範囲と理由を記録する。

5. 各ステップ後に対象コミット、処理済みファイル、指摘、関連する変更の要点、未確認事項、次の処理、追加指示を保存する。不要になったコードのメモリ上の参照を破棄する。必要なコードは固定したコミットから再取得する。

6. 各ステップの要点と指摘を照合し、APIとクライアント、定義と呼び出し元など複数ファイルにまたがる不整合を確認する。要約だけで問題を断定せず、必要な元コードを再取得して確認する。

7. 指摘ごとに重要度、対象ファイル・行、問題、影響、根拠、必要に応じた修正案を提示する。対象外・未確認のファイルとその理由も示す。

8. ユーザーが指摘を質問・選択・編集し、明示的に承認した内容をGitHubに投稿する。投稿時にヘッドコミットを再確認し、更新されていればユーザーに通知する。

### 割り込みとメモリ

- オーケストレーターはステップ間で追加指示と停止要求を確認する。追加指示の受付と反映を区別して表示する。進行中のAI応答への即時反映は保証しない。

- 方向転換ややり直しが必要な場合は、現在の処理に停止を要求し、停止を確認してから新しい指示で再開する。停止は即時完了するとは限らない。

- 初期版は1セッションにつき1ステップずつ順番に処理する。複数セッションの同時実行は別途制限する。

- PR全体を常にメモリに保持しない。目次・処理状態と、現在のステップに必要な差分・関連コードだけを扱う。GitHub MCPレスポンスやAI入力の上限も設ける。

- 通常のCloud Runローカルファイルシステムもメモリを消費するため、一時ファイルへの書き出しをメモリ節約の前提にしない。

- 仮のメモリ設定と同時レビュー数を使ってピークメモリ・取得量・AI入力量・時間を計測し、上限を確定する。

## 12. 開発段階

### 第一段階（MVP）: GitHub読み取りとコンテキスト管理

GitHubでログインし、許可したリポジトリの情報をチャットで読み取りながら、会話・取得情報によるAIコンテキストの肥大を防ぐ仕組みを検証する。

- GitHubログインとGitHub Appによる対象リポジトリの接続を行う。GitHub MCPを読み取り専用に設定し、許可された範囲のリポジトリ、ファイル、PR、Issueを参照する。

- ユーザーは自身のOpenAI APIキーをセッションごとに入力する。キーの一時保持と最大1時間の取り扱いは本書の認証方針に従う。

- WebSocketでメッセージ・追加指示・停止を送信し、応答や進捗を受信する。

- AIは質問に応じてGitHub MCPを使い、取得できた情報に基づいて回答する。参照元へのリンクと、取得・確認できなかった範囲や理由を示す。処理中の追加指示は適切な区切りで受け付ける。

- 第一段階のGitHub操作は読み取りのみとする。自動レビュー、GitHubへの書き込み・投稿、コード・テストの実行、大きな画像やバイナリの解析は対象外。

- 会話と最低限の実行状態を保存し、切断時はAI処理を停止または認証待ちにして、再接続時に復元する。異なるユーザーのセッションや情報を分離する。

第一段階の確認条件: GitHubログイン・リポジトリ接続・AIキー入力後、許可したリポジトリ、ファイル、PR、Issueについて質問し、GitHub MCPで取得した情報と参照元に基づく回答を得られる。追加指示・停止・切断後の会話復元を確認し、AIキーが期限内に破棄され、ログや永続ストレージに残らないことを検証する。

#### 第一段階のコンテキスト管理

- 会話履歴の保存と、各AI呼び出しに含めるコンテキストを区別する。履歴全体やリポジトリ全体を毎回渡さない。

- まずPR概要やファイル一覧など小さな情報を取得し、質問に必要なファイルや差分だけを段階的に追加取得する。

- 1回の取得サイズ、ファイル数、ツール呼び出し回数、AI入力トークン数に上限を設ける。数値はモデルや実測に基づき決める。

- 直近の会話と必要な要点を維持し、古い履歴・不要なコード全文を繰り返し渡さない。要約で失われた詳細は、必要に応じて保存済み履歴や対象コミットから再取得する。

- 差分・ファイル内容は必要な範囲を一時的にメモリに保持し、利用後は参照を破棄する。上限やエラーで未確認の範囲と理由を画面に示す。

- 会話を重ねた際のAI入力トークン数、取得サイズ、取得回数、ピークメモリと所要時間を計測し、上限内での動作・重複取得の抑制を検証する。対象PRや重要な指示を維持できること、要約後に必要な詳細を再取得できることも確認する。

### 第二段階: PRレビュー

第11節のレビュー計画、ステップ実行、関連コードの追加取得、全体照合、結果提示を実装する。GitHubへの投稿はユーザーの確認後に行う。

あわせて第13節の実装・PR作成を実装する。レビュー投稿と同じく、GitHubへの書き込みはユーザーが内容を確認し明示的に実行した場合に限る。

## 13. 実装・PR作成フロー設計（仮案）

ユーザーがチャットで依頼した変更をAIが計画・実装し、ユーザーの確認後に新しいブランチとPRを作成する。既存のGitHub App OAuth、セッションごとのAIキー、WebSocketでの指示・停止、Firestoreのチェックポイントとlease、読み取りのコンテキスト管理をそのまま利用する。

### 前提と範囲

- 依頼は自由文で受け付ける。Issue URLやPR URL（レビュー指摘への対応など）を添えた場合は、その内容を背景として読み込む。

- 対象はテキストのソースコード・設定・ドキュメントの追加・変更・削除。画像・バイナリ・生成ファイル・リネーム、`.github/workflows` 配下の変更は初期版の対象外とする。

- アプリ内ではコード・ビルド・テストを実行しない（2026年10月31日決定）。検証は作成したDraft PRに対する対象リポジトリのCIに委ね、AIは未検証であることと確認してほしい点を明示する。アプリ内でのテスト実行は将来の拡張とする。

- PRはDraftで作成する。マージ、既存ブランチへの書き込み、強制プッシュ、デフォルトブランチへの直接コミットは行わない。

- 以下の数値は検証前の仮置きで、実測に基づいて調整する。

### 処理手順

1. ユーザーが依頼を入力する。AIは既存の読み取りの仕組みで関連コードを調べ、目的・不明点を整理する。前提が曖昧な場合は実装に進まずチャットで質問する。

2. 開始時のベースブランチとコミットSHAを固定し、実装計画を提示する。計画には変更・追加・削除するファイル、各ファイルの変更方針、対象外とすること、想定されるリスク、確認すべきテストを含める。ユーザーが計画を承認するまで変更を作成しない（ユーザー待ち）。計画を提示する前に、変更・削除するファイルが固定コミットに実在し、追加するファイルが存在しないことを確認する。一致しない場合はAIに計画を作り直させ、承認しても適用できない計画を提示しない。

3. 承認後、関連するファイルのまとまりごとに変更を作成する。1ステップあたり原則最大5ファイル。AIは固定コミットの元コードを再取得したうえで、検索・置換ブロックまたは新規ファイル全文の構造化出力を返す。サーバーは置換対象が一意に一致することを確認して適用し、適用できない場合は理由を添えてAIにやり直させる。各ステップ後に処理済みファイルと未完了の作業を保存し、追加指示・停止を確認する。

4. 全ファイルの変更後に、変更全体の差分と計画を照合し、定義と呼び出し元の不整合、計画からの漏れ、意図しない変更を確認する。必要に応じて既存のPRレビュー処理を自分の変更差分に適用する。（初期実装では未実装。各区切りの要点を後続の区切りへ引き継ぎ、計画にあって変更されなかったファイルを未確認事項に記録する。作成したPRは既存のPRレビューで確認できる。）

5. 変更内容をファイルごとの差分として画面に表示する。ユーザーはチャットで修正を依頼でき、初期実装では依頼を元の依頼に加えて計画から作り直し、差分を再表示する。ユーザーはブランチ名（既定は `ai-factory/` で始まる名前）、PRタイトル、PR本文を確認・編集する。PR本文にはAIが作成したこと、依頼の要約、未検証事項を含める。

6. ユーザーが「PRを作成」を明示的に実行した時点で、サーバーが書き込みを行う。GitHubのGit Data APIで固定したベースSHAからblob・tree・commitを作成し、新しいブランチのrefを作成し、Draft PRを作成する。完了後にPRのリンクを表示する。

7. 作成後も同じセッションでの追加修正依頼を受け付ける。PRがオープンでブランチが前回のコミットのままなら、このセッションが作成したブランチにだけ追加コミットを行う。PRがマージ・クローズ済みなら最新のデフォルトブランチから新しいブランチで作り直す。追加コミットではプッシュ前にブランチの先頭が前回記録したSHAと一致することを確認する。他者の更新があれば中断してユーザーに通知する。

8. PRのCI結果は読み取りで確認し、失敗した場合はログの要点を示す。失敗の修正はユーザーの依頼があった場合に手順3以降を繰り返す。

### GitHubへの書き込みと安全性

- GitHub Appに Contents と Pull requests の書き込み権限を追加し、権限の内容と用途を画面に明示する。書き込み権限を許可していないリポジトリでは計画と差分の確認までとし、PR作成を無効にする。

- 書き込みはGitHub MCPを使わず、サーバー側の専用アダプターから固定ホスト・固定リポジトリ・固定操作だけで行う。AIは書き込み操作を直接呼び出せず、変更内容の提案だけを返す。AIの出力や対象リポジトリ内の文書に含まれる指示によって、対象リポジトリ、ブランチ、操作の種類を変更しない。

- 書き込みのたびにユーザーのリポジトリ権限を確認する。コミットはユーザーのGitHub Appユーザーアクセストークンで行い、作成者が分かるようにする。

- 変更するパスは計画で承認したファイルに限る。計画外のファイルを変更する必要がある場合はユーザーの再承認を求める。`.git`、`.github/workflows`、`.github/actions`、`CODEOWNERS`、パストラバーサル、シンボリックリンク、サブモジュールへの書き込みを拒否する。

- 変更差分に秘密情報らしい文字列（APIキー・トークン形式）が含まれる場合は作成を拒否する。

- 書き込みは操作IDを付けて状態を保存し、再試行時は記録したブランチ・コミット・PR番号を確認してから続きの操作だけを行う。同じブランチ名のrefが既に存在する場合は上書きしない。PR作成の重複は、同じheadブランチの既存PRを確認して防ぐ。

- 停止要求が書き込みの途中で届いた場合、完了した操作は取り消さず、どこまで完了したかを表示する。

### 状態・保存とメモリ

- セッション状態は既存の状態を利用する。計画承認待ちと作成確認待ちはユーザー待ちとして表示する。

- 保存するのは依頼、計画、固定ベースSHA、処理済みファイル、作成したブランチ・コミット・PR、未検証事項。変更後のファイル内容は、ユーザー・セッション・コミットに紐づけた期限付きキャッシュに保存し、セッション状態に含めない。キャッシュの期限切れ後は計画と固定コミットから再作成する。

- 仮の上限: 変更ファイル最大20件、1ファイル最大100 KiB、変更差分の合計最大200 KiB、AI呼び出し最大100回・30分。上限に達した場合はユーザー待ちとし、保存位置から再開できる。

- ベースブランチが固定SHAから進んでいてもPRは固定SHAから作成し、差分の確認画面とPR本文でベースの更新を通知する。

### 確認条件

- 書き込み権限を許可したリポジトリで、チャットの依頼から計画の提示、計画の承認、変更差分の確認を経てDraft PRを作成できる。

- ユーザーが承認するまでGitHubへの書き込みが行われない。計画外のファイル、禁止パス、既存ブランチへの書き込みが拒否される。

- 実行中の追加指示・停止、切断後の復元、保存位置からの再開ができる。

- 書き込み途中の失敗・再試行で、ブランチ・コミット・PRが重複しない。

- 作成済みPRへの追加修正が同じブランチへのコミットとして反映され、他者の更新があれば中断される。

- 他ユーザーのセッションやブランチを操作できず、認証情報や変更内容が永続ストレージ・ログに残らないことを検証する。
