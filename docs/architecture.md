## 認証

### GitHubログインとFirebase

GitHub AppのOAuthをstate・PKCEで行い、GitHub `/user` で確認したIDからFirebase UIDを生成する。Firebaseカスタムトークンは同一OriginのHTTP応答でだけ返し、URLに入れない。ブラウザーはFirebase ID tokenをAPIへ送り、APIで失効も確認する。

### GitHubトークンのCookie

- GitHub user access tokenはAES-256-GCMで暗号化したHttpOnly / SameSite=Lax Cookieに保持する。本番はSecure。
- 復号鍵はSecret Managerから供給する。CookieのAADでOAuth state用とGitHub用の用途を分離する。
- GitHubの有効期限または8時間の早い方で再ログインする。refresh tokenは保持せず、更新は再ログインで行う。
- Firebaseの本人認証とCookieのUIDを照合する。

### WebSocket接続とlease

WebSocketはOriginと最初の認証フレームを検証し、ユーザーごとの接続leaseを取得する。1ユーザーにつき1接続。45秒のleaseを10秒ごとに更新し、保存時にも同一leaseと期限をトランザクションで検証する。

インスタンスが突然終了した場合、最大45秒後に新しい接続が最後の保存状態を取得できる。アプリは切断時にAIを再開せず、ユーザーの操作を待つ。

## AIキーの扱い

- OpenAIキーはモジュール内のメモリにのみ保持する。Pinia・localStorage・sessionStorage・URLに保存しない。
- キー入力から最大1時間で破棄し、送信直前にも期限を確認する。セッション切替・終了・ログアウト・ページ終了でも破棄する。
- サーバーは各実行に必要な間だけキーを参照し、完了・キャンセル時に参照を外す。通常チャットは最大3分、PRレビューは最大15分、接続は最大55分。切断・ブラウザー終了後の継続実行は保証しない。
- チャットへ一般的なキー形式を入力した場合は拒否する。モデルにキーを本文として渡さず、モデルが当該実行の認証情報を出力した場合も保存を拒否する。
- OpenAIリクエストは `store:false`。

メモリの参照破棄はアプリによるコピーの利用停止を意味し、ランタイム／OS上のバイトの即時ゼロ化やOpenAI側でのキー失効を保証しない。

## 通常チャットの読み取りとコンテキスト

### 質問の解釈と調査方針

各質問の最初のAI判断で、最新の質問と会話から目的・調査方針・回答の深さを仮説として整理し、最初の読み取り判断も同時に行う。以後の判断にはこの方針と取得結果を渡し、追加指示があれば見直す。方針は実行中のメモリだけに保持し、取得した事実や利用者の指示とは区別する。

構成の質問ではルート一覧に加えて、必要に応じてREADMEや主要設定・エントリーポイントを読み、役割やつながりの説明に必要な根拠を集める。質問の範囲が狭い場合は不要な取得を避ける。意図整理専用のAI呼び出しは増やさない。

### GitHubからの読み取り

モデルは許可された構造化読み取り要求だけを返す。対象owner/repo、コミット、MCP操作名はサーバーが決定する。GitHub権限を毎回確認し、MCPの `/readonly` と `X-MCP-Readonly:true` を併用する。任意URL、書き込み、コード実行の経路を提供しない。

読み取る対象は次のとおり。

- 通常チャットのファイルはセッション作成時のデフォルトブランチのコミットから取得する。
- PRレビュー開始時にベース・ヘッドのSHAを固定し、以後の関連コードはヘッドを参照する。
- PR本文・一覧・コメントは取得時点の情報。
- レビューではPRメタデータ／差分を読むRESTアダプターと、関連コード／コメントを読むMCPアダプターを併用する。

### 上限値

| 制限 | 初期値 |
| --- | --- |
| ユーザー本文 | 4,096バイト |
| 追加指示1件／AIへ渡す追加指示 | 各4,096バイト。新しい指示から優先して保持 |
| 1質問あたりのGitHub取得 | 最大6回、ファイル要求は最大5件 |
| MCP 1応答 | 最大100 KiB。上限超過は未確認理由として表示 |
| 1取得結果のAI投入 | 最大8,000バイト。後半省略を明示 |
| AI用コンテキストJSON | 最大24 KiB。直近最大6メッセージ・要点2 KiB・指示・直近2取得結果 |
| OpenAIリクエストJSON全体 | 最大40 KiB（システム指示・出力schema込み） |
| AI出力 | 最大4,096トークン／呼び出し、回答16 KiB、要点2 KiB |
| 1質問あたりのAI呼び出し | 最大7回 |
| 会話保存 | 最大200メッセージ、本文合計300 KiB |
| 同時WebSocket接続 | 1インスタンス4接続、1ユーザー1接続 |
| 外部HTTP / 1実行 | 60秒 / 通常チャット3分・PRレビュー15分 |

入力トークンそのものの事前カウントではなく、まずUTF-8バイト数と呼び出し回数で小さく制限する。実トークン数はOpenAI usageから集計する。上記の出力上限との組み合わせで利用量を制限するが、料金通貨の上限を保証するものではない。料金換算は未実装。

### 取得結果の保持

取得結果は実行内のメモリにのみ保持し、同一要求は再取得しない。保存するのは会話、要点、対象コミット、参照リンク、未確認理由、利用量。古い会話本文は必要なら履歴画面で読める。コードの詳細は固定コミットから再取得できる。モデルによる要約は事実の証明ではなく、欠けた詳細は再取得して確認する。

### 判断回数の配分

通常チャットは各AI判断に `chatBudget` を渡し、残りの取得回数・ファイル要求数・今回を含むAI判断回数を知らせる。

- 最大7判断のうち最後の1判断は回答のために予約する。6取得の終了後または最終判断では、構造化出力の `read` を `null` に限定する。
- 5ファイル要求を使い切ると `file` を取得候補から除く。
- 取得済み情報と要約から回答・未確認範囲をまとめる。同一要求のキャッシュ利用が続いた場合も、追加のAI判断や取得を上限外で行わない。
- AIが最終回答の制約を守らなかった場合は追加取得せず、保存済みの調査メモと未確認の案内を返す。

### ヒープ値

ヒープ値は処理の区切りで観測したGoプロセス全体のHeapAllocの最大値。OS RSS、瞬間ピーク、セッション単体のメモリ使用量を示すものではない。実PRでの負荷試験と上限調整は今後必要。

## 保存と削除

### Firestoreの保存先

`users/{uid}/sessions/{id}` に状態・会話・要点・参照元・利用量・固定対象・ExpiresAtを保存し、`users/{uid}/locks/connection` に接続leaseを保存する。UIDは検証したトークンからのみ採用する。ブラウザーからのFirestore直接読み書きは全拒否する。

### 保存期限と削除

セッションは作成から30日後にアクセス不可。FirestoreのExpiresAtフィールドにTTLを設定するとバックグラウンドで物理削除される。TTLは即時ではない。

本人はサイドバーから即時削除できる。接続中は削除を拒否し、UIが切断・lease解放後に再試行する。Firebase認証ユーザーの一括アカウント削除・運営用管理画面は未実装。

### GitHub読み取りのキャッシュ

コミットに固定されたファイル・ディレクトリ取得は、リポジトリ・コミットSHA・パスをキーにFirestoreの `githubReadCache` へ1時間保存する。READMEも対象。

- 毎回GitHubでリポジトリ権限を確認してから利用し、失敗した取得は保存しない。
- 期限切れは読み取り時に拒否し、Firestore TTLで後から削除する。
- PR・Issueなどコミットに固定されない情報は対象外。
- キャッシュが利用できない場合は通常どおりGitHubから取得する。

## コード表示とREADMEの概要

### 実装ファイルの保存

チャットの回答・取得元リンク・レビュー計画に列挙されたソースファイルは、会話内の「実装ファイル」から個別または一括保存できる。

`GET /api/v1/sessions/{id}/file?path=...&commit=...` はセッション所有者を確認し、サーバーが保持するリポジトリと会話・レビューのコミットに取得を限定する。既存の読み取りキャッシュを経由し、未取得ならGitHubから読み込む。削除ファイルや変更前の指摘はbase、通常の変更ファイルはheadを使用する。

ファイル本文は会話履歴に追加せず、ブラウザーのIndexedDBに利用者・セッション・リポジトリ・コミット・パスを分けて保存する。

- 保存期限1時間、1ファイル100 KiB、全体10 MiBの上限を設け、期限切れ・古い保存から削除する。
- 再読み込み時に保存済み内容を復元し、ログアウト・セッション削除時にも削除する。
- ブラウザー保存や取得が失敗したファイルは一覧にエラーを表示し、再試行できる。
- パスの列挙自体はファイルの実在確認を意味しない。

### コード表示パネル

コード表示はチャットの右側の独立したパネルへ遅延ロードし、highlight.jsのGitHub配色と行番号を使う。長い行は横スクロールでき、言語・行数・バイト数・コミットSHA、原文のコピー、対象コミットのGitHubリンクを表示する。

コードを閉じると参照情報の表示に戻り、セッション切り替え時には閉じる。狭い画面では右から重なるパネルとして表示する。コードは実行せず、未対応の言語もHTMLをエスケープして表示する。

### READMEの概要

新しいセッションの最初の実行時に、固定コミットのREADME.mdを取得し、目的・主要なファイルやディレクトリの役割・技術構成だけをAIで短く要約してセッションに保存する。READMEの入力は最大8,000バイト、保存する概要は最大1,400バイト。

- 概要は後続のチャットとレビューに背景として渡し、作成元のコミットと省略の有無も添える。PRのheadとは異なる可能性があり、レビュー指摘の証拠には使わない。
- README取得・要約に失敗しても実行は続ける。既存セッションには自動作成しない。
- 同じリポジトリ・コミットであれば、概要をセッション間で1時間再利用する。利用前にGitHubのリポジトリ権限を確認し、コミットが変わった場合やキャッシュの期限切れ・利用不能時は改めて生成する。概要生成に失敗した結果は保存しない。

## PRレビュー

### レビューの開始

通常のWebSocket `message` でPR取得・レビュー依頼を受ける。専用セッションの作成・レビュー開始ボタンは不要。

1. 取得に成功したPR番号を `ActivePullRequest`（`activePullRequest`）に保存する。取得失敗時に対象番号は変更しない。
2. 「このPRをレビューして」という依頼では、AIが構造化出力 `startReview` を返す。
3. サーバーが対象リポジトリを固定し、PR番号・実行モード・レビュー初期化を先に保存してから、同じ会話で分割レビューへ進む。

対象PRの決め方は次のとおり。

- 番号0は会話内で最後に取得したPRを参照する。
- 旧セッションはサーバーが記録したPR参照リンクも利用する。
- 明示的なPR番号の指定も可能で、リポジトリは会話の接続先に固定する。
- 対象不明時は同じチャットで番号を尋ねる。

概要や指摘についての質問には通常の回答を返す。従来の `review` コマンドも互換用に維持し、`resume` で保存した計画・差分のバイト位置・全体照合のカーソルから再開する。新規レビューは過去のレビュー状態を置き換える。

### 保存する情報

取得したPRタイトル・本文の短い抜粋、SHA、ファイル目次・要点・指摘・未確認事項だけを保存し、レビュー状態には差分・元コードを含めない。差分とコミット固定の元コードは別の期限付きキャッシュに保存する。

### 差分の取得と計画

GitHub RESTのPR取得と変更ファイル取得は、固定ホスト／リポジトリ／PR番号だけに限定する。

- [GitHubのPR API](https://docs.github.com/en/rest/pulls/pulls) の変更ファイルを1ページ1ファイルで取得する。
- 計画作成時の差分はPRのベース・ヘッドを再確認後に期限付きキャッシュへ保存し、レビュー時や再開時に再利用する。
- 差分は1片最大16 KiBに分割し、欠落や破損があれば再取得する。
- キャッシュは1時間で期限切れとなり、利用前にリポジトリへのアクセス権を確認する。コメントはキャッシュしない。
- ディレクトリごとに実装・テストを最大10ファイルのグループにまとめ、先頭200ファイルまで計画する。メタデータ取得も各ファイル後に保存する。

### バッチの組み方

差分は関連する実装・テストを最大10ファイル、共通トークナイザー（埋め込みのo200k_base）で約2万トークンまでまとめる。

- 大きい差分だけhunk・関数の先頭を優先し、行境界で分割する。
- 途中のhunkでも元の左右の行番号を引き継ぎ、長すぎる1行・不完全なhunk・差分欠落・対象外の形式を明示する。
- 保存済みの5ファイル単位の計画も変更せず、同一ディレクトリの連続グループを最大10ファイルまでまとめて再開する。
- AI応答とPRヘッドを確認した後、バッチに含む全ファイルの位置を一度のチェックポイントで保存する。保存前に停止・切断した場合は未保存のバッチを再確認する。

### 入力と出力の上限

- システム指示・スキーマ用に4,000トークンを予約し、入力全体約3万トークン以内を目安にする。Claude・Geminiを含めモデル固有の正確なカウントではなく、実利用量は各プロバイダーのusageを別途記録する。
- レビュー用JSONには256 KiB、APIリクエストには512 KiBのバイト上限も設ける。通常チャットの24 KiB／40 KiB上限は維持する。
- 関連コード・コメントは区切りごとに最大5回取得し、各24,000バイトまで・最大5件を保持する。
- 入力上限に近い場合は背景情報から減らし、次に関連コードを短くして省略を記録する。
- レビューは1応答最大8,192トークン、指摘最大10件、要点2,048バイトまで返せる。

### 全体照合

全体照合は入力予算に入る複数グループの要点・指摘の短い抜粋と、それまでの照合要点をまとめて渡す。

要点だけで複数ファイルの指摘を確定しない。同じ区切りで異なる2ファイル以上の元コードを再取得した場合だけ、入力内のパス・行に対応する指摘を採用する。モデルが元コードを取得しなかった区切りは「要点の照合のみ」と表示する。この方式は全依存関係の網羅を保証せず、省略や取得上限は未確認事項に残す。

### PR更新の検出

PRファイルAPIは可変なので、取得前後・計画と差分の保存前・全体照合の保存前に、PRのベース・ヘッド・変更ファイル数を再確認する。変更時は `pr_changed_create_new_review` で中断し、チャットでの再レビューを案内する。旧スナップショットの保存済み結果は対象SHA付きで残す。

### 実行の上限と再開

PRレビュー1回の継続実行は最大100モデル呼び出し・15分、実利用量で入力50万／出力6.4万トークン。20回ごとの中断は行わず、停止・切断・実行予算の上限まで続行する。

- 回数・トークン上限は次のAI呼び出し前に判定するため、トークン上限は最後の1呼び出し分だけ超える場合がある。
- 実行予算・時間上限では `user_wait` とし、手動で保存位置から再開できる。
- APIキー期限・WebSocket接続期限を超えて継続しない。切断時は既存の復元フローを利用する。
- 1取得は100 KiB、指摘は最大50件、JSON化したチェックポイントは450 KiBまで。
- 保存応答を待ってから次の区切りへ進み、停止要求後の結果は採用しない。
- 追加指示は実際にモデルへ渡したものだけを反映済みにする。

### 保存期限とアクセス

レビュー結果は通常のセッションと同じユーザー分離・lease・30日の保存期限・削除に従う。セッション一覧には重いレビュー状態を含めず、選択時に取得する。GitHubへの書き込み・コードやテストの実行は提供しない。

## 実装・PR作成

### 全体の流れ

チャットのAIが構造化出力 `startImplementation` を返すか、利用者が `implement` コマンドを送ると `RunKind=implement` になる。状態は `Session.Implementation` に保存し、次の順に進む。各区切りの保存応答を待ってから次へ進む。

```text
planning → plan_ready → editing → verifying → ready → publishing → checking_ci → published
```

| 段階 | 内容 | 説明する節 |
| --- | --- | --- |
| 計画 | 基準コミットを読み、変更するファイルと受け入れ条件を決める | [計画](#計画) |
| 変更の作成 | 承認された計画に沿って区切りごとに変更を作る | [変更の作成](#変更の作成) |
| 整合性確認 | 変更全体をAIが読み直し、公開できるかを判定する | [整合性確認](#整合性確認) |
| PR作成 | AIを使わずサーバーがDraft PRを作る | [PR作成とGitHubへの書き込み](#pr作成とgithubへの書き込み) |
| CI確認 | 対象コミットのチェック結果を待つ | [CIの確認](#ciの確認) |

### READMEの自動参照

実装の計画・編集・整合性確認には、同じ基準コミットのルート `README.md` を `projectDocumentation` として自動で渡す。既存の既定動作や省略時の振る舞い、旧データとの互換性を取りこぼさないため、モデルが選んだ読み取りと別に保持し、取得結果の直近件数による削除の対象にしない。

- 1回のRunner実行で一度だけ読み、AI呼び出しは追加しない。
- 入力は最大8,000バイトとし、省略・取得不能を明示する。
- READMEが存在しない場合も実装を続ける。
- 本文は仕様の参照データであり、利用者の変更依頼や権限を上書きする指示としては扱わない。

### 計画

#### 基準コミットとパス一覧

計画（`implementTask.mode=plan`）はデフォルトブランチの最新コミットを基準として固定し、そのコミットのファイル・ディレクトリの取得とコード検索を合わせて最大10回行える（直近5件を保持）。

計画の前に、基準コミットのツリーを再帰取得した全ファイルのパス一覧をAIへ渡し、パスの推測を防ぐ。一覧は `node_modules`・`vendor`・`dist`・`build` を除き、最大3,000件・30,000バイト。超える場合は浅い階層を優先し、行単位で切る。一覧を取得できない場合は一覧なしで計画を続ける。

#### コード検索

コード検索は大文字小文字を区別する文字列検索で、query・prefix・cursorだけをAIが指定する。

- 検索対象のリポジトリと基準コミットはサーバーが固定し、既存のパス一覧から保護パスやバイナリを除いたファイルをRESTで読む。
- 1回最大40ファイル・30ヒットで区切り、ファイル内の行位置も引き継ぐcursorで続きを取得できる。
- 内容はトークン・リポジトリ・コミット・パスに紐づけてキャッシュし、毎回権限を確認する。
- 一覧の省略・読めないファイル・続きの有無を結果に含め、行の抜粋では秘密情報らしい文字列を伏せる。
- 検索は計画時と整合性確認時に許可し、それぞれの取得枠を使い切った後はスキーマ・サーバー検証の両方で禁止する。

計画中に読んだファイルと検索でヒットしたファイルは `ContextFiles`（最大8件）として保存する。

#### 計画の検証と見直し

- 計画は最大20ファイル、`create/update/delete` と方針を含み、サーバーがパスを検証する。`.git`、`.github/workflows`、`.gitmodules`、バイナリ・ロックファイル、パストラバーサルは拒否する。
- 提示前に、変更・削除するファイルの実在と追加するファイルの不在を確認し、一致しなければAIに作り直させる。
- 続けて一度だけ、計画したファイルの隣のテスト（`_test`・`.test`・`.spec`）と、計画時に読んだが計画に入れなかったファイル（最大10件）を示して見直させる。
- 曖昧な依頼ではAIは計画せず質問を返す。

#### 計画外のファイルの追加提案

変更の作成中、AIは計画外のファイルを `additionalFiles`（パス・action・方針・理由、1回最大5件）で提案できる。

1. サーバーがパス・実在・上限・見送り済みを検証し、有効なものを `PendingFiles` として `amend_ready` で保存して止まる。
2. 利用者が `implement_amend`（approve / decline）で決める。approveなら計画に追加し、完了済みの区切りを保ったまま依存関係に従って未完了の区切りを並べ直す。declineなら `Declined` に記録して続行する。
3. 元の区切りで変更されなかったファイルは、決定後に再実行する。

有効な追加提案と変更のどちらもない場合はAIに再出力させる。

### 受け入れ条件

計画には `acceptanceCriteria`（最大20件）を必須とし、依頼を観測可能な条件へ分解する。各条件にid・要件・根拠コードのパス・確認方法を保存し、計画と一緒に承認する。

CI修正では失敗行ごとの `ジョブID:L行番号` を `failureRefs` に対応させ、未対応の失敗があれば計画を再出力させる。追加修正でも既存条件を保持する。

### 変更の作成

#### 区切りと依存順

計画の各ファイルには先に内容を決める必要があるファイルを `dependsOn` で指定できる。

- 未知のパス・自己参照・重複を拒否し、依存先が利用側より先になるように区切りを作る。
- 循環する依存は強連結成分としてまとめ、同じ区切りで処理する。循環が5ファイルを超える計画はAIに見直させる。
- 独立した変更は従来のディレクトリ順を基準に最大5ファイルでまとめる。
- 入力上限による分割でも循環のまとまりは分断しない。

変更（`mode=edit`）はこの順序で行う。

#### 元ファイルと応答の形式

元ファイルはMCPではなくRESTのraw取得で基準コミットから読み、AIへ渡す。AIは更新を検索・置換ブロック、新規をファイル全文で返す。サーバーは区切り内のファイルと計画どおりのactionだけを受け付け、各searchが元ファイルで1か所だけ一致する場合に適用する。適用できなければ理由を添えて再出力させる。

#### 区切りに渡す文脈

区切りをまたぐ名前や型の不整合を防ぐため、各区切りには次を渡す。

- `previousChanges`: 前の区切りで作成した変更の差分。各6,000バイト・合計20,000バイトまで。
- `context`: 変更済みファイルの現在の内容を優先し、`ContextFiles` と計画中の他の更新ファイルを加えた内容。各12,000バイト・合計36,000バイトまで。`modified` は変更後、`deleted` は削除済み。

入力上限を超える場合は取得結果、`context`、`previousChanges` の順に省く（AIを呼ばない再試行は呼び出し回数に数えない）。それでも超える区切りは分割する。

#### 変更後のファイルの保存

変更後のファイルは1時間の期限付きキャッシュ（`githubReadCache`、ランダムな `CacheID` とバージョンで区別）に保存し、書き込みを読み戻して確認する。セッション状態にはパス・action・サイズだけを保存し、`CacheID` はブラウザーへ返さない。

#### 編集中の追加取得

編集中のAIによる追加の `file` 取得は、生成済みのファイルなら変更後の内容を返し、削除済みなら削除を通知する。未変更のファイルとディレクトリだけを固定ベースから取得する。生成内容の期限が切れた場合は古い内容に戻さず `implementation_changes_expired` で停止する。

#### 検索・置換が適用できないとき

検索・置換の原文が見つからない、または複数箇所に一致する場合は、同じ形式を繰り返さず `line_ranges` に切り替える。

1. 原文を行番号付きで渡し、ファイル全体のSHA-256、両端の行番号・照合用の原文、置き換え後の範囲だけをAIに返させる。
2. サーバーはハッシュ・範囲・両端の照合・重複のなさを確認し、入力原文の後ろから適用する。

空白を無視した曖昧な検索や全文の置き換えへの自動緩和はしない。範囲外のバイト列とCRLFの改行は保持し、不正な変更は一切保存しない。失敗した編集の番号・一致件数・分類だけをログに記録し、コード本文は記録しない。

#### 応答形式が不正なとき

計画・編集でAIの応答形式が不正な場合は、操作の排他条件などを訂正として渡し、連続3回の失敗まで（最大2回の自動再試行）、各段階の呼び出し予算内で再試行する。認証・通信エラーはこの対象に含めない。再試行前の保存に失敗した場合は続行しない。

停止後はセッションの状態に合わせてパネルを「中断」と表示し、同じパネルから保存済みの状態を再開できる。完了・失敗後に古い進捗を表示し続けない。

### 整合性確認

#### 確認の範囲

計画作成では編集対象と確認対象を分ける。編集中に全文を確認して変更不要と分かったupdateは、`unchangedFiles`（path・reason）で縮小候補として記録する。編集担当の提案だけでは計画から削除せず、作成・削除・既存ドラフトの取消しにも使わない。検証では差分のない計画ファイルをコードの確認対象に必ず加え、検証担当が変更不要を独立に判断する。全受け入れ条件とコードの確認範囲を満たし、指摘・静的な未確認がなくなった場合だけ、実効計画と実装順から対象を外し、依存先の参照を更新する。元の計画項目と理由は `planAdjustments` に保存し、画面とPR本文で確認できる。受け入れ条件は削除・弱体化せず、そのファイルも根拠コードとして残す。旧セッションの再検証でも同じ照合を行い、確認できないファイルは公開を止める。

検証結果の `issues` は確認済みの不具合、`unverified` は静的に要求達成を確認できない点、`deferredChecks` は公開後のCIで実行するビルド・テストとする。実行前という事実だけで公開を止めず、実際のコードの不足・未達・根拠不足は従来どおり公開を止める。モデルの自由文から「CI」などの語句を検索して未確認事項を自動除外する処理は行わない。

計画・編集・検証のモデル呼び出しでは、通信エラーと429・一部5xxを最大2回、指数バックオフとジッターを入れて再試行する。Geminiの時間切れは分割できる編集を優先して分割し、分割できない編集や他の段階では最大1回再試行する。各段階の試行回数・実装全体の呼び出し回数・時間上限を維持し、再試行前に状態を保存する。停止・認証失敗・権限不足・拒否・保存失敗・保存期限切れには適用しない。GitHubへの書き込みは保存済みの公開状態を使う既存の再開経路で扱う。検証時の不正なJSON応答も各プロバイダー共通で最大3回の連続不正まで訂正を試みる。

検証中の未確認事項は、追加検索で新しいコード断片が得られた場合も解消の根拠にできる。同じパス・行・本文の検索結果は重複として扱い、ページ情報の変化だけでは新しい根拠にしない。検索断片をファイル全文の確認として登録せず、受け入れ条件のコード確認範囲は別に検証する。

編集後は `verifying` に保存して、読み取り専用の `implementTask.mode=verify` で計画・変更全体の整合性を確認する。

- 変更セットをサーバーで再検証する。
- すべての変更後コード（削除は削除元）をUTF-8境界で8,000バイト以内の部分に分け、原則48,000 JSONバイト以内の区切りでAIに渡す。差分は補助情報として省略し得るが、コード本文は省略しない。
- 複数区切りなら各区切りの契約の要約を最後に照合する。
- 変更外の計画時参照ファイル・受け入れ条件の根拠ファイル・隣接テストも全文で確認する。
- 検証中はファイル取得・コード検索を合わせて最大12回行え、検索には生成済みコードの一致も含める。

指摘・修正候補・未確認点は `Verification` として保存する。

#### 自動修正

根拠のある指摘に修正候補がある場合、承認済みパスと操作の範囲で最大2回、自動編集と全体確認を繰り返す。

- 修正対象の入力は作成済みの最新コードを使う。createは再編集時も固定ベースに対するcreateのまま扱う。
- 計画外のファイルは追加承認を待ち、見送り済みのファイルは再提案しない。
- 回数・修正方針・次のステップを保存してから編集する。

#### 受け入れ条件の判定と公開の可否

各条件にmet/unmet/unverified・根拠・確認したパスを返させ、未取得コードを根拠とする達成判定を拒否する。未確認事項が返った場合は追加調査を促し、新しいコードを取得せずに未確認を消すことを認めない。

- 最終結果を実装パネル・PR本文に表示する。
- 指摘・未確認・条件の未達や確認漏れが残れば `verification_blocked` として公開を止める。`implement_verify` で再調査できる。
- すべて静的に確認できた場合だけ `ready` に進む。
- 受け入れ条件のない旧計画は再計画を案内する。
- 確認自体が失敗した場合は `verifying` のまま止まり、再開時は編集を繰り返さず整合性確認をやり直す。

これはAIによるコードの読み直しであり、ビルド・テストの実行や成功を意味しない。

#### 言語別ナレッジ

静的な整合性確認にはバックエンドへ埋め込んだ `backend/internal/agent/verification_knowledge/` の言語別ナレッジを `verificationKnowledge` として渡す。

- 登録対象はGo、JavaScript/TypeScript、Python。
- 現在の確認区切りと追加取得したコード（部分取得・検索抜粋を含む）のパスの拡張子から選び、最後の全体照合では全確認対象の言語を引き継ぐ。対象外の言語や文書だけの区切りには付与しない。
- 依頼と既存契約を優先し、該当するエラー経路・状態変更・nil/欠損・参照共有・並行処理を確認するための観点とする。新しい要件や書き込み権限にはしない。
- 指摘の根拠はルールID・確認したパス・具体的な操作とともに既存の指摘・受け入れ条件の根拠へ記録し、不足するコードは追加取得または未確認にする。
- ナレッジのバージョンと言語IDをモデル呼び出しログに残し、コード本文は記録しない。
- ナレッジの選択に追加の外部取得・モデル呼び出しは行わず、ビルド・テストの実行先は既存のGitHub CIとする。

追加・更新手順は同ディレクトリのREADMEに記載する。

### 公開前の追加依頼

未公開の作成済み変更への追加依頼では、最新の依頼を4,096バイト内に必ず残し、既存の依頼の長さを調整する。

- 保存済みの変更を新しいドラフトへ引き継ぐ。固定ベース・承認済みパス・生成済み内容を引き継ぎ、新しいキャッシュIDと版へ全内容を検証してコピーしてから計画する。コピー完了前に失敗してもコピー元の情報を保存しておき、期限切れ時は停止する。
- 今回編集が必要なファイルだけをステップにし、既存の変更を計画と差分に保持する。再計画でもactionは固定ベースに対する操作（create/update/delete）のまま維持する。追加質問がある場合も既存の計画と差分を保持する。
- 今回編集するファイルには現在の保存内容を渡す。`preserveExisting=true` のファイルは変更不要なら応答から省略できる。同じ内容が返された場合も保持として扱い、保存済みキャッシュを書き直さず編集を進める。
- 未実装ファイルの省略や保存期限切れを完了扱いにはしない。生成後は保持した内容を含む変更全体を再検証してから公開可能とする。
- 編集応答のpathは現在の工程のファイルだけに制限する。CI修正では確認済みのPRヘッドにあるファイルも、同時に失敗原因を直す実際の変更がある場合は維持できる。保持だけで失敗したPRを修正済みにしない。
- チャットにはコードやキャッシュIDを渡さず、変更済みパスと直前の整合性の指摘を渡す。画面の差分キャッシュは版と変更回数の両方で更新する。

作成済みPRへの追加変更でブランチが外部更新された場合は、未公開の差分を別ベースに自動適用せず停止する。

### 追加指示

追加指示は1件4,096バイト・セッション全体の履歴上限内で受け付ける。AI入力は最新の指示から4,096バイト内に保持し、古い指示を省略した場合は明示する。実装・通常チャット・レビューで同じ規則を使う。

### CIの失敗ログ

CIのチェック結果は許可したリポジトリと固定コミットのREST APIから最大20件取得し、全件でない場合は明示する。ActionsのジョブIDは同じリポジトリの詳細URLから検証して抽出し、チェックIDをそのままログ取得に使わない。

一覧中のすべての失敗ジョブのログを、秘密情報をマスクして計画・編集・整合性確認へ渡す。

- ログは最大8 MiBを走査し、先頭や途中も含めた失敗行の一覧を優先して保存する。残りの入力予算で周辺5行までを均等に追加する。
- ジョブごと16 KiB、CI根拠全体48,000バイトまで。
- 超過・読み取り失敗・チェックの省略・実行中のジョブがあれば全件確認とは扱わず、CI修正を止める。
- CI根拠は通常の取得結果と分けて固定し、後続の読み取りや入力削減で消さない。取得が失敗した場合はその事実を記録する。

CI失敗の修正依頼ではチェック結果や失敗ログを取得できなければAI呼び出し前に停止する。403の場合はChecks/Actionsの読み取り権限とインストール先の更新・再ログインを案内する。CIと無関係なPRの変更はこの制限の対象外とする。AIが変更できない理由を返した場合は未確認事項として保存・表示し、変更や処理位置を進めずに中断する。

### ログに残す情報

実装ログは次を記録する。

- モデル呼び出しの開始・完了
- 段階・ステップ・呼び出し回数・試行回数・再試行回数
- 許可リストにあるエラーコードと応答検証の分類（操作競合・検証段階の不一致・件数や長さの上限など）
- 操作フィールドの有無と回答のバイト数
- 読み取り元（生成内容／固定ベース）
- 整合性確認の指摘件数・自動修正回数と対象件数

コード本文・モデル応答・プロバイダーの任意のエラーメッセージは記録しない。Geminiの不正な意図を破棄した場合も、空欄／長さ超過という分類だけを記録する。

### PR作成とGitHubへの書き込み

PR作成はAIを呼ばずサーバーの書き込みアダプターが行う。

1. 毎回リポジトリのpush権限を確認する。
2. Git Data APIでblob・tree・commitを作成し、新しい `ai-factory/` ブランチのrefを作る。
3. Draft PRを作成する。

安全のため次の制約を設ける。

- 各パスは基準コミットのtreeを1階層ずつたどって確認し、シンボリックリンク・サブモジュールを拒否し、既存ファイルのモード（実行ビット）を維持する。
- 既存ブランチへの上書き・強制プッシュ・デフォルトブランチへの書き込みは行わない。
- 変更内容・PRタイトル・本文に認証情報らしい文字列があれば拒否する。

### 書き込みの再試行と既存PRへの追加

完了した書き込み（コミット、ref、PR番号）は1段階ごとに保存し、再試行時は残りだけを行う。refが既に同じコミットを指していれば作成済みとみなし、同じheadブランチのPRがあれば再利用する。

PR作成後の追加依頼は作成したブランチの最新コミットを基準に新しい計画から始める。プッシュ前にブランチがそのコミットのままであることを確認して `force:false` で更新する。他者の更新があれば `branch_moved` で中断する。

別のセッションやアプリで作成した既存PRへの修正依頼は、チャットの `startImplementation.pullNumber` か「実装を依頼」の「修正するPR番号」で指定する。

- 計画の前にPRを取得し、オープンで、同じリポジトリの `ai-factory/` で始まるブランチの場合だけ、そのheadを基準・`ExpectedHead` として同じ手順で追加コミットする。
- それ以外は `pull_request_closed`・`pull_request_from_fork`・`pull_request_not_ai_branch` で拒否する。
- 追加依頼ではPRのチェック結果を読み、失敗した全ジョブの失敗行と周辺行を計画の材料にする。

### 実行の上限

AI呼び出しは1回の実行で最大100回・30分、出力は1呼び出し最大16,384トークン、入力は約6万トークン（共通トークナイザーの推定）と256 KiBまで。アプリのAPIプロセス内では対象コード・ビルド・テストを実行しない。

### CIの確認

PR作成後は `checking_ci` で対象コミットのチェックを10秒間隔・最大5分確認する。

- 成功・失敗・実行待ち・未確認を別に保存し、他のコミットの結果・スキップ・一覧の省略・チェック0件を成功にしない。待機中も保存する。
- 未完了なら `ErrCIWaiting` で実行を区切り、実装の `checking_ci` とセッションの `ci_wait` を保存する。
- ブラウザーは接続中に10秒後の `resume` を送って確認を続ける。この継続ではAIキーを送らず、モデル呼び出し・再公開・完了メッセージの追加も行わない。
- 切断中はアプリの確認が止まり、再接続後に継続する。中断後はCI確認だけ再開して重複公開しない。
- `stop` は実行中と区切りの間の待機の両方を停止する。
- 画面は待機状態と固定コミットの `/commit/{sha}/checks` リンクを表示し、ジョブ一覧やログは表示しない。
- 結果取得不能や不完全な結果は未確認として止め、CI成功と区別する。
- 1回の待機（最大5分）を終えてもチェックが1件も登録されない場合は、CIのないリポジトリやブランチでの無限待機を避けるため未確認として止める。
- `CIWait=0` はデモ・評価用に1回だけスナップショットを取得する。

CI確認後の操作は次の2つ。計画・追加ファイル・コミットの承認は従来どおり利用者が行う。

- `implement_check_ci`: AIキーなしで再確認する。
- `implement_fix_ci`: 元の要求とPRを保持し、全失敗ログから新しい修正計画を作る。
