# 実装編集・照合・再試行の問題整理

更新日: 2026-11-02（時刻は日本時間）。実装状況は [PR #21](https://github.com/jeorp/ai-factory/pull/21)（[#22](https://github.com/jeorp/ai-factory/pull/22)〜[#24](https://github.com/jeorp/ai-factory/pull/24) を含む）を基準とする。手順1・2は実装済みで、実モデルでの再評価（手順3）は残っている。

## 現状

実モデルで、編集を生成できず `implementation_edit_failed` になる失敗を2回確認した。どちらも `gemini-3.5-flash-lite`、エフォートは `medium`。モデルAPIへの呼び出しは成功しており、返された編集をサーバーが拒否している。

原文との照合や計画にない操作の拒否は機能していた。一方、モデルに渡す出力制約と、拒否後に返す訂正情報が不十分で、同じ誤りを繰り返して呼び出し上限を消費した。失敗した工程の変更は保存されず、整合性確認・PR公開には進んでいない。

原文の境界行を返す修正と、追加取得を挟んでも訂正を保持する修正は実装済み。ただし、その後の実行では別の操作種別の誤りで上限に達した。これを受けて、パスごとの操作をスキーマで固定し、構造の誤りを適用前に具体的に訂正する修正を #22 で加えた。実モデルでの復旧成功はまだ確認できていない。

## 実ログで確認した経緯

対象ファイルはいずれも `backend/internal/agent/implement_prompts.go`。

### 02:50〜02:52：計画と操作種別が一致しない

追跡ID: `3PUGCW7V5BgC1Dve8wPpvEd0BLqLGpW9`。所要時間は約106秒。

| モデル呼び出し | 動作・拒否理由 |
| --- | --- |
| 1〜3 | 入力の `files.action` は `update` なのに、応答は `create` とファイル全体の本文。毎回 `change_action_not_planned` で拒否。 |
| 4 | 同じファイルを追加取得。前回の訂正が次の入力にも残っていることを確認。 |

最後の検索文字列は20,767バイト、原文は20,771バイトで、どちらも44行。文字列比較で少なくとも30行目の「さ」が「し」に変わっていることを確認した。長さだけの問題ではなく、原文を照合用にそのまま返せていない。

最初の3回で操作種別の誤りを繰り返し、4回目の取得も同じ呼び出し枠を使ったため、行範囲方式へ切り替えて再試行する機会が残らなかった。この実行では、新しい境界行の訂正情報を使って復旧できるかは評価できていない。

同一パスの重複は応答本文で確認した。サーバーは1件目の検索不一致で先に終了しているため、この実行の最終エラーが `change_path_duplicate` だったわけではない。

## 原因と対応状況

| 問題 | アプリ側の原因・影響 | 状態 |
| --- | --- | --- |
| 照合用の原文をモデルが変形する | 大きな検索文字列や長い境界行の正確な再現に失敗する。検索置換から行範囲への切り替えだけでは回復しなかった。 | 正しい境界行を返す修正済み。モデルの引用ミス自体を防止できたとは未確認。 |
| 不一致の訂正に正しい原文がない | 使い方の説明だけを返し、同じ誤った境界行を繰り返せてしまう。 | 修正済み。`editFailure` にパス・ハッシュ・行数・失敗した範囲の正しい境界行を含める。 |
| 追加取得で訂正が消える | 正常なモデル応答を受けた時点で `correction` を消し、取得後の編集へ引き継がない。 | 修正済み。回帰テストと02:50の実ログで保持を確認。 |
| 計画と違う `action` を生成できる | 編集スキーマの `path` は工程内に限定されるが、`action` は常に `create/update/delete` を許可する。パスと計画上の操作が対応づけられていない。 | 修正済み（#22）。工程の各パスを計画上の `action` 1つに固定した `anyOf` の変種を `changes.items` に使う。create・deleteは `edits`/`lineEdits` を `maxItems: 0` で空に制限する。Claudeの構造化出力は `maxItems` を受け付けないため送信時に除き、この制限はサーバーの検証だけで効く。deleteの `content` はスキーマで制限せず、サーバーが無視する。実プロバイダーがこのスキーマを受理するかは未確認。 |
| 操作種別の訂正が具体的でない | `change_action_not_planned` が対象パス・期待操作・提出操作を持たない。訂正が「計画どおりに」という説明になり、場所が空・編集番号が0になる。 | 修正済み（#22）。`editFailure.changeIssues` に提出位置・パス・期待操作・提出操作を渡し、訂正文にも同じ値と操作別の書き方を含める。 |
| 同じパスを複数返す | `changes` の応答構造でパスの一意性を保証していない。適用処理で重複を拒否するが、先行する編集エラーがあると重複の診断まで到達しない。 | 修正済み（#22・#23）。原文照合の前に全項目の構造を検証し、重複は最初の位置とあわせて返す。重複した項目の操作や欄の誤りも同じ訂正で返す。 |
| 有効な編集に至る前に上限へ達する | 1工程の5回には、追加取得や適用で拒否された応答も含まれる。形式不正の連続回数制限とは別に、操作種別の拒否は工程の枠を消費する。 | 現行の制限。制約・訂正を改善した後に予算配分を評価する。単純な上限増加は未実施。 |

### 実装済みの訂正処理

`implementTask.editFailure` は固定された原文からサーバーが作る情報で、モデルが返した不正確な文字列の再利用ではない。行範囲が有効なら正しい `expectedStart` / `expectedEnd` を渡し、同じ範囲の再試行でコピーできるようにした。

空行、範囲外、4096バイトを超える行、境界に使えない改行文字を含む行は確認文字列として返さない。切り詰めた原文を正解として渡すことも避ける。古い `sourceHash` のエラーには対象パスを付け、実際のハッシュを訂正情報へ渡す。

この情報を作れるのは対象パスを保持した編集エラーであり、現在の `change_action_not_planned` などには適用されない。原文不一致への修正が、操作種別の誤りも直したという意味ではない。

## 観測のために修正した問題

| 問題 | 対応 |
| --- | --- |
| 詳細ログの再試行番号が0になる | モデル入力JSONには含めないサーバー内部の実行状態から `call/attempt/retry_count` を記録。 |
| Dockerの長いログで日本語が文字化けする | 詳細payloadをUTF-8の境界を保って小さなレコードに分割。`payload_id/chunk_index/chunk_count` で復元する。 |
| 不正UTF-8で分割が進まなくなる | 分割前に不正な文字列を置換し、進行しなくなる経路を修正。 |
| 元コードと提出内容を比較できない | 詳細ログに期待・実際の境界行、周辺コード、ハッシュ、計画・提出の操作を記録。 |

詳細ログは `AGENT_DEBUG_LOG=1` を指定したローカル開発だけで有効になる。本番設定とCloud Runでは有効化を拒否する。既知の認証情報はマスクするが、依頼文・コード本文を含むため、生ログはこの文書やPRへ添付していない。収集・復元方法は[開発ガイド](development.md#ローカル限定の詳細debugログ)を参照する。

## 次に直す順序

### 1. 計画から出力制約を作る（対応済み）

対象パスと許可された `action` の組をスキーマに反映する。単一ファイルだけでなく、create/update/deleteが混在する工程でも対応を保つ。全操作の共通enumや、工程内の操作一覧だけに絞る方法では、混在時の取り違えを防げない。

制約の表現方法は各プロバイダーが受け付けるスキーマで確認する。応答スキーマに制約を入れても、サーバー側の計画・パス・操作検証は継続する。

### 2. 構造の誤りを編集適用前に診断する（対応済み）

工程外パス、同一パスの重複、計画と違う操作を、原文への適用前に検証する。訂正情報には対象パス・提出位置・期待操作・提出操作を含める。通常ログには固定コードと必要なメタデータを記録し、原文は含めない。

既存の編集不一致への訂正と同様に、追加取得を挟んでも情報を保持する。安全のため、モデルの `create` をサーバーが黙って `update` に置き換える対応は採らず、正しい編集を再生成させる。

実装: `validateProposalStructure`（[implement_changes.go](../backend/internal/agent/implement_changes.go)）が工程外パス・同一パスの重複・不正または計画と違う操作・操作ごとの欄の誤りを全項目について先に集め、1件でもあれば原文に触れずに拒否する。訂正（[implement_edit_recovery.go](../backend/internal/agent/implement_edit_recovery.go)）は工程内のパスと列挙値だけを返し、モデルが書いた工程外パスなどの自由文は再掲しない。通常ログ `implement_change_rejected` は固定コード・位置・操作だけを記録する。構造の拒否では行範囲方式へ切り替えない。回帰テストは [implement_structure_test.go](../backend/internal/agent/implement_structure_test.go)。

### 3. 実モデルで回復率と呼び出し消費を確認する

制約・訂正を改善してから、今回の依頼をGemini Lite / mediumで再評価する。大きなファイル全体をsearchに返す傾向、操作の取り違え、同一パスの重複、訂正後の再失敗を記録する。必要なら初回から行範囲方式にする案や、範囲をより小さくする入力設計を比較する。これらは未採用の案であり、成功するとの前提は置かない。

その結果を見て、追加取得と編集の予算配分や、同一失敗が続いた場合の終了・方式変更を判断する。費用・待ち時間・停止後の再開も確認し、上限を増やすだけの対応にしない。

あわせて次の点も実ログで確認する。どちらも現時点では不具合と判断していない。

- モデルが工程内のファイルを `changes` から省略すると、拒否せず「計画にあるが変更されなかったファイル」として未確認に記録し、工程を進める。
- 形式不正（`edit_format_mismatch` など）で再試行すると、訂正文は形式の訂正に置き換わる。`editFailure` の構造化情報は残る。

- LF/CRLF、末尾改行の有無、実際の行数、空行・範囲外・上限超過の境界、古いハッシュの回帰テスト。
- 詳細ログの分割・日本語復元・認証情報マスク・不正UTF-8の回帰テスト。

モデル応答を制御した回帰テストの成功は、実Geminiが毎回正確な編集を生成する証拠ではない。02:50の実行も失敗しており、実モデルでの再評価は残っている。

### 完了条件

- 単一・複数ファイル、操作が混在する工程で、各パスに計画どおりの操作を要求できる。（#22で対応、回帰テストで確認）
- 誤った操作やパス重複を適用前に検出し、具体的な訂正を返せる。追加取得後もその訂正が残る。（#22で対応、回帰テストで確認）
- 拒否された工程で一部の変更だけを保存したり、工程番号を進めたり、公開したりしない。
- 修正した応答だけを保存し、変更全体の整合性確認を経てから公開可能にする。
- 実Geminiで今回の依頼を再評価し、成功・失敗、各呼び出しの用途、拒否理由、使用トークン・所要時間を記録する。
- Lite特有かどうかを結論づける場合は、同じ入力・エフォート条件・判定基準で別モデルとも比較する。現状の2実行だけでは特有とは判断しない。
