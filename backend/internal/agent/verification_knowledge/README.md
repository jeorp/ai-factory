# 言語別の静的検証ナレッジ

実装エージェントがコードを読み直す際の確認観点を管理する。実行基盤や外部データベースは追加せず、MarkdownをGoのembedでバックエンドへ同梱する。実行中に対象リポジトリからこのカタログを上書きしない。

| 登録ID | ファイル | 対象拡張子 |
|---|---|---|
| 共通 | common.md | 登録言語を確認するときに共通で付与 |
| go | go.md | .go |
| javascript-typescript | javascript-typescript.md | .js / .jsx / .mjs / .cjs / .ts / .tsx / .mts / .cts |
| python | python.md | .py / .pyi |

現在の版は `language-verification/v1`。言語仕様に関する記述と出典は2026-11-01に確認した。バージョンに依存する挙動を追加するときは適用条件も明記する。

## 適用方法

`implement_knowledge.go` が現在の確認対象パスから登録済みの言語だけ選び、共通観点と合わせて `verificationKnowledge` に入れる。複数言語の変更はそれぞれを選び、同じパスは重複させない。分割確認後の全体照合や、検証中に全文取得した関連コードにも適用する。未取得のリポジトリ一覧からは選ばない。未登録言語・文書のみの場合は従来の静的確認を続ける。

依頼・追加指示・既存契約が判定の基準。ルールは適用条件付きの確認観点であり、nilと空を常に区別するなどの要件を追加しない。指摘にはルールID、実際に読んだパス、関数・分岐・操作、契約との矛盾を示す。不足があれば追加取得し、未確認を残す。結果は既存のissues、criteria.evidence、unverifiedへ記録し、受け入れ条件のIDを増やさない。

静的な判断なので、テスト成功や競合の不存在の証拠にはしない。コード実行は既存のGitHub CIで行う。ナレッジの版・言語IDは既存のモデル呼び出しログに残る。

## 追加・更新手順

1. 対象言語のMarkdownへ、識別可能なルールID、適用条件、確認対象、誤検知を避ける条件、一次資料へのリンクを書く。
2. 新しい言語は `implement_knowledge.go` にembed宣言と登録ID・拡張子・本文の対応を追加する。READMEだけ追加しても登録されない。
3. 内容を変更したらカタログの版も更新し、言語選択・混在・重複・追加取得・全体照合のテストを実行する。全言語を選んでも通常のパス数で10 KB以内に収める。
4. 本体の回帰テストを通し、検出精度の改善を主張する場合は、既存の独立したevalで正しい実装と不正な実装の双方を測る。ナレッジがモデルへ渡るテストと、実モデルが不具合を見つける評価を区別する。

カタログは検証入力に含まれるため、長いコード例や依頼と無関係な一般論を詰め込まない。採点用の隠しテスト・参考解答・認証情報は登録しない。
